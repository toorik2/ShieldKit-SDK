# RFC-0001: pluggable ceremony-backed verifier profiles

Status: accepted for `g0-v2`

Date: 2026-07-23

## Problem

The 54,949-byte verifier baseline is a fixed-VK research candidate with
hardcoded verifier material. It is useful for building and measuring the
protocol, but its locally controlled initialization cannot become a production
trust assumption.

The protocol must allow development to proceed with locally generated setup
material while ensuring that a later multi-party randomness ceremony can
produce a proper verifier bundle without rewriting wallet, state-transition, or
conformance logic.

## Decision

Introduce a versioned verifier-profile interface. A bundle binds:

- proof system and curve;
- relation and canonical public-input ABI;
- circuit and constraint-system hashes;
- verification key and BCH verifier scripts;
- proving artifacts;
- setup mode and transcript hashes;
- toolchain and reproducibility metadata; and
- one derived profile identifier.

The initial build and Chipnet tests may use a locally initialized
`development-only` bundle. It must be visibly labeled and cannot satisfy
production setup or release claims.

A later multi-party randomness ceremony emits a distinct
`ceremony-production` bundle implementing the same interface. Replacing a
bundle creates a new immutable protocol profile and a new instance. No deployed
instance, genesis, verification key, or covenant is hot-swapped or upgraded.

Wallet and conformance logic depend on the interface and manifest, never on
hardcoded keys. Profile-specific proving and verification code is selected by
the authenticated profile identifier.

## Consequences

- The development setup permits immediate end-to-end Chipnet engineering.
- Production setup trust is not laundered from the development build.
- The circuit/public-input ABI can be tested for compatibility across bundles.
- A ceremony or verifier change requires new artifacts, vectors, profile ID,
  genesis, and qualification evidence.
- Funds never move automatically between profiles; any migration is an ordinary
  user-authorized action permitted by the old profile.

## Invalidated gates and evidence

- G0 is reopened to add the verifier-profile boundary.
- G1 is reset because setup and verifier feasibility must be evaluated against
  the new bundle contract.
- No G2 or downstream evidence exists.
- The measured 54,949-byte development baseline remains valid only as a sizing
  and implementation baseline.
